# 50 - 低分演员头像：体检、根因与修复

> GitHub issue: https://github.com/luckwalter/LocalMeta/issues/1
> 修复提交：`93e793a`（缺图判定 + 分辨率门槛）、`a8e4242`（重刮结果与认证头写法）

> 现象：升级并跑过 LocalMeta 之后，一部分演员头像变成了 1XX 像素的小图。
> 结论：**不是 Jellyfin 压缩，也不是 Metatube 变差**，是本地源里混着低分图 + 插件误判"缺图"后无条件覆盖。
> 体检时间：2026-10-06；环境 Jellyfin 12.1.0（C:\Jellyfin），插件 LocalMeta 0.3.0.0。

## 二、根因（三层，缺一不可）

### 第 1 层：源头数据本身就残

| 项 | 实测 |
|---|---|
| gfriends_plan.json 人数 | 1276 |
| avatars/ 里真正有图的 id | 673（覆盖率 53%） |
| 其中 0 字节 webp | **673 个全部为 0**（导出脚本下载 webp 全失败，且没清理） |
| 其中 0 字节 jpg | 7 |
| jpg 里 1XX 小图 | 114（占 17%） |

### 第 2 层：缺图判定在 12.1.0 下失效（主因）

12.1.0 把 Person 的 `BaseItems.Id` 与 `Peoples.Id` **脱钩**了，图片记录挂在 Person 实体那一侧：

```
有图且挂在 BaseItems.Id（Person 实体）: 2460 人
有图且挂在 Peoples.Id                :  678 个（其中 673 个还是本插件自己写的）
抽样：几乎所有演员 Peoples.Id 图数=0、BaseItems.Id 图数=1、两 Id 不相同
```

而 `LoadTargets()` 里是这样判的：

```csharp
SELECT COUNT(*) FROM BaseItemImageInfos WHERE ItemId = <Peoples.Id> AND ImageType=0
```

查的永远是那个空的 Id → **全员被判"缺图"** → 即使 `OverwriteExisting=false`，
"只补空"也照样变成"全部覆盖"。Metatube 刮到的高清头像就这么被本地小图顶掉。

### 第 3 层：没有分辨率门槛

`TryGetAvatarPath()` 只做 `File.Exists`，不看尺寸也不看是否 0 字节。
所以 125x125 的缩略图和 0 字节坏文件都被当成有效头像复制进 `metadata/People/<演员>/folder.jpg`。

时间线对得上：673 个头像文件的 mtime 集中在 2026-10-05 12 点那次批量写入，
106 个 1XX 里 101 个是同一批。

## 三、已做的修复

| # | 修复 | 位置 |
|---|---|---|
| 1 | `HasImage` 同时查 `Peoples.Id` 和 Person 实体 `BaseItems.Id`，并用物理文件兜底 | `Tasks/LocalMetaBackfillTask.cs` |
| 2 | 新增 `MinAvatarWidth`（默认 300，按**短边**判定，不误杀 400x600 竖图） | `PluginConfiguration.cs` |
| 3 | 新增 `AvatarGate`：解析 JPEG/PNG/WebP 文件头取尺寸；挡掉 0 字节与低分源图 | `Sources/AvatarGate.cs` |
| 4 | 图片 provider 走同一套门槛，刷新元数据时不会再把高清图换成小图 | `Providers/LocalMetaPersonImageProvider.cs` |
| 5 | `TryGetAvatarPath` 从 `File.Exists` 改为"存在且非空" | `Sources/LocalMetaSources.cs` |
| 6 | 配置页加「头像最小尺寸」输入框 | `Configuration/configPage.html` |

不引入任何图像处理依赖（插件目录只允许托管程序集，带原生库会让整个插件被判 Malfunctioned），
尺寸靠手写的文件头解析。

部署结果：2026-10-06 01:23 重启后日志
`Loaded plugin: "LocalMeta" "0.3.0.0"`、`[LocalMeta] 载入资料源 2 个`，无 LocalMeta 相关 ERR。
配置已写入 `<MinAvatarWidth>300</MinAvatarWidth>`。

修复后行为：源图短边 < 300 就跳过，日志会记
`任务完成：补图 X / 补简介 Y / 源图过小跳过 Z`。

分类：

- 源图即低分，走 Metatube 重刮：**99**
- 源里没头像（含 7 个 0 字节坏图），走 Metatube 补：**13**

调用方式（Jellyfin 12.1.0 必须用 Person 实体的 `BaseItems.Id`，用 `Peoples.Id` 会 400）：

```
POST /Items/{personItemId}/Refresh
     ?MetadataRefreshMode=FullRefresh
     &ImageRefreshMode=FullRefresh
     &ReplaceAllImages=true
```

认证头 **只能** 用这一种，实测另外两种都返回 401：

| 写法 | 结果 |
|---|---|
| `Authorization: MediaBrowser Token="<key>"` | **200** |
| `X-Emby-Token: <key>` | 401 |
| `?api_key=<key>` | 401 |

匿名调用一律 401。

API key 可以用 `tools/avatarscan/_apitoken.txt` 里那个（本机 jellyfin.db 的 ApiKeys 表，
Name=`localmeta-repair`）。批量脚本 `tools/avatarscan/refresh_avatars.py`：

```bash
python refresh_avatars.py --limit 10          # 先试 10 个
python refresh_avatars.py --skip 10           # 续跑剩下的
python refresh_avatars.py --restore           # 还原刷之前的备份
```

刷之前会把原图备份到 `Data\LocalMeta_backup\avatars_before_refresh\`，
`ReplaceAllImages=true` 是先删旧图再下新图，刮不到就剩空，所以这层保险必须有。

### 实测结果

首轮 10 个：变好 10 / 没变 0 / 变差 0。
`125x125 -> 1024x1536`、`125x125 -> 1416x2125`、`0x0 -> 600x900`（坏图也补上了）。
说明 MetaTube 手里确实有高清图，之前只是被本地小图顶掉了。

## 六、遗留建议

1. **导出脚本要清理失败的下载**：673 个 0 字节 webp 说明 gfriends 只提供 jpg，
   webp 全部 404。留着这些空文件除了占地方，还会被旧版代码当成有效头像。
2. **头像覆盖率只有 53%**（673/1276），想再提升得换或补头像源。
3. 每次升级大版本后，都要重新验证"缺图判定"这类直查 sqlite 的逻辑——
   这已经是第二次栽在 schema 变更上了。
