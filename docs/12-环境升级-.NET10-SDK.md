# 环境升级：.NET 9 SDK → .NET 10 SDK

日期：2026-10-05
目标：Jellyfin 已升到 12.1.0（宿主 `net10.0`），开发环境跟着升到 .NET 10，
插件重定 `net10.0` 并引用 `Jellyfin.Controller 12.1.0`。

结论：**插件代码一行没改**，接口签名经 apiprobe 取证确认与 10.11 完全一致。
这次改的全是构建环境、目标框架和产物清理方式。

---

## 一、升级前的环境

| 位置 | 内容 | 说明 |
|---|---|---|
| `%USERPROFILE%\.dotnet` | SDK 9.0.318 + runtime 9.0.20 + packs | 之前用官方脚本装的 |
| `C:\Program Files\dotnet` | runtime 8.0.14 / 8.0.17 / 9.0.7 / **10.0.12** | 只有 runtime，无 SDK，PATH 里排前面 |

**PATH 陷阱**：直接敲 `dotnet` 会命中 `C:\Program Files\dotnet`（没有 SDK），
报 `No .NET SDKs were found`，看着像没装。`build.ps1` 已做探测，不用改 PATH。

账号是**非管理员**，所以 SDK 只能装到用户目录 `%USERPROFILE%\.dotnet`
（装到 Program Files 需要管理员权限）。

---

## 二、安装 .NET 10 SDK

最新是 **SDK 10.0.401**，自带 runtime 10.0.12（含 ASP.NET Core Runtime，
正好补齐了之前缺的那一块）。

```powershell
# 官方脚本，默认装到 %USERPROFILE%\.dotnet，不需要管理员
& .\dotnet-install.ps1 -Version 10.0.401 -Architecture x64 -InstallDir "$env:USERPROFILE\.dotnet"
```

### 踩到的坑：脚本解压会静默中断

现象：脚本没打印完成信息，退出码非 0，但 `dotnet --list-sdks` 已经能看到
`10.0.401`。一编译就炸：

```
error : 无法解析 SDK"Microsoft.NET.Sdk"
error :   SDK 解析程序"Microsoft.DotNet.MSBuildWorkloadSdkResolver"返回 null
error MSB4236: 找不到指定的 SDK"Microsoft.NET.Sdk"
```

**判据**：`sdk\10.0.401\Sdks` 目录不存在；目录体积只有 262M（完整是 409M）。

**修法**：不必删目录重来，直接下载 zip 覆盖解压即可（缺失文件会补上，多余文件无害）：

```
https://builds.dotnet.microsoft.com/dotnet/Sdk/10.0.401/dotnet-sdk-10.0.401-win-x64.zip
```

解压后核对三项：`sdk\10.0.401\Sdks`、`sdk\10.0.401\Sdks\Microsoft.NET.Sdk`、
`shared\Microsoft.NETCore.App\10.0.12`。

> 顺带一提：批量删除 `sdk\10.0.401`（1345 个文件）会被安全策略拦下
> （`SAFE_DELETE_BULK_CONFIRM_REQUIRED`，阈值 50）。覆盖解压正好绕开这个问题。

`%USERPROFILE%\.dotnet` 下所有 9.x 组件，用 PowerShell 一次清完：

## 五、兼容性检查

### 取证目录必须是真在跑的那个（重要）

本机有两个 Jellyfin 目录，**对着错的那个取证等于白取证**：

| 目录 | `jellyfin.runtimeconfig.json` | 实际身份 |
|---|---|---|
| `C:\Jellyfin` | `tfm: net10.0`，runtime 10.0.12 | **12.1.0，真在跑的**（自包含发布） |
| `C:\Program Files\Jellyfin\Server` | `tfm: net8.0`，runtime 8.0.14 | 10.11 的残留 |

判断方法：看 `jellyfin.runtimeconfig.json` 里的 `tfm`，或看日志里的 `Storage path`。

不同命名空间，与插件用到的 `Jellyfin.Data.Enums.ImageType` 无关。

## 六、产物清理方式改了：黑名单 → 白名单

`Jellyfin.Controller 12.1.0` 的依赖图比 10.11.6 大得多。`dotnet publish` 之后，
产物目录里除了插件自己，还混进来这些**宿主本来就有的**第三方 dll：

```
Diacritics.dll   Emby.Naming.dll   ICU4N.dll(13MB)   ICU4N.Transliterator.dll
J2N.dll   Microsoft.EntityFrameworkCore*.dll(3 个)   NEbml.Core.dll
Newtonsoft.Json.dll   Polly.dll   Polly.Core.dll
MediaBrowser.*.dll(3)   Jellyfin.*.dll(4)
```

外加一个 `runtimes/` 目录（原生库，会让插件被判 Malfunctioned）。

原来的 `RemoveHostAssemblies` 按前缀删 `MediaBrowser.*` / `Jellyfin.*`，
对第三方依赖无效——**它们没有统一前缀**。所以换成白名单 `PrunePublishDir`：

| 保留 | 理由 |
|---|---|
| `Jellyfin.Plugin.LocalMeta.dll` | 插件自身 |
| `Microsoft.Data.Sqlite.dll` | 直读直写 jellyfin.db |
| `SQLitePCLRaw.core.dll` | SQLite 引擎托管封装 |
| `SQLitePCLRaw.batteries_v2.dll` | 初始化 SQLitePCLRaw |
| `SQLitePCLRaw.provider.e_sqlite3.dll` | 指定 e_sqlite3 原生引擎 |

其余全删，`runtimes/` 整个目录删掉。实测一次清理掉 19 个多余程序集。

删掉 `runtimes/` 后 SQLite 仍可用：Jellyfin 宿主进程已加载自己的 `e_sqlite3.dll`，
SQLitePCLRaw 的 provider 在进程内复用（实测能正常读 `javboss.db`）。

`Newtonsoft.Json` 也在被删之列，但宿主 `C:\Jellyfin\Newtonsoft.Json.dll` 提供，
运行时不受影响（插件只在解析 `gfriends_plan.json` 时用它）。

## 七、遗留提示

- 编译有一条警告 `NU1903`：`SQLitePCLRaw.lib.e_sqlite3 2.1.10` 有已知漏洞告警，
  来自 `Microsoft.Data.Sqlite 9.0.0`。升级需重新验证 SQLite 原生库加载，
  收益不大风险不小，暂不处理。
- 之前"net9.0 插件在 net10.0 宿主下也能跑"的结论仍然成立；这次同步到 net10.0
  是为了和宿主对齐，不是被迫的。
